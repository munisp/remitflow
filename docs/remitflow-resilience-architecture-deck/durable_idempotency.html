Financial mutations survive cache loss
A completed payment request is not remembered by a process or a cache. It is reserved, bound, leased, and replayed through a tenant-scoped PostgreSQL correctness path.
01 / BIND

Verified request scope

Tenant, user, operation, idempotency key, and request hash establish the only valid replay identity.

→
02 / RESERVE

Durable row lease

PostgreSQL records a processing state, lock token, and expiration before the money-moving operation begins.

→
03 / EXECUTE

One protected mutation

Concurrent requests observe the lease rather than execute again; database isolation protects the tenant boundary.

→
04 / REPLAY

Bound response state

A matching completed request receives the stored result. A changed payload conflicts instead of being replayed.

RESILIENCE POSITION
Redis improves speed. PostgreSQL decides correctness when a worker, cache, or process disappears.
